# Pattern Layout Studio V2.1 — Export background and favicon

Date: 2026-10-09

## Scope

1. Add a branded browser tab icon, without describing that fix in the website's release announcement.
2. Allow the user to choose export background colors in the export modal.

## Browser favicon

- `public/favicon.svg` uses the project's layered-page visual mark.
- `index.html` links the icon through `%BASE_URL%favicon.svg?v=2`, respecting GitHub Pages' `/pattern-layout-studio/` subpath.
- No favicon changelog entry is added.

## Export background choices

- **原图背景（默认）**: preserves existing behavior by using the detected source background.
- **纯白背景**: fills the page with opaque white.
- **自定义颜色**: uses an HTML color picker, shows a HEX code, and provides color presets.
- **透明背景**: keeps the export canvas's untouched area at Alpha 0.

The selection is state-owned by `src/app/App.tsx`, is shared between current-page PNG and all-pages ZIP export, and remains selected when the export dialog closes and reopens.

The resolved color is passed to `renderLayoutPage` / `buildPagesZip`. The rendering code skips the canvas background-fill step for `transparent`; original `PatternPart` images remain unmodified.

## Invariants

- Source RGB/Alpha and part dimensions are not rewritten.
- Packing, gap and page positioning are unaffected.
- Export background affects only the downloaded image and not the editor canvas preview.
- PNG DPI `pHYs` metadata remains intact.
- All exported pages within the same ZIP use the selected background.

## Automated tests

`tests/export-background.mjs` checks:

- browser favicon resolved at GitHub Pages' base path, returns SVG and HTTP 200;
- four modal background options, custom HEX selection, modal selection persistence;
- exact RGBA in the PNG background for detected/white/custom/transparent;
- original part pixel RGB remains unchanged;
- PNG `pHYs` metadata is present;
- multi-page ZIP includes all pages and retains DPI;
- the export drawer remains within a 390px mobile viewport.

Run `node tests/v2-smoke.mjs` afterwards to verify existing workspace behavior.

The actual GitHub Pages release is only complete when the final `main` commit's Pages workflow has successful build + deploy jobs.
